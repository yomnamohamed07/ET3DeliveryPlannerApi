🚚 ET3 Delivery Planner

A simple and deterministic delivery trip planner built with ASP.NET Core Web API and Entity Framework Core.

The system organizes deliveries into vehicle trips while respecting:

🚛 Maximum vehicle capacity of 10 kg per trip

⚡ Delivery priority

📍 Area grouping

✅ Data validation

🔄 Deterministic behavior

The solution focuses on being simple, readable, maintainable, and easy to explain, as required by the technical challenge.

📌 Overview

The application receives a list of deliveries and organizes them into vehicle trips.

Each delivery contains:

Property	Description
Id	Automatically generated by the database
Area	Destination area
Priority	Lower number means higher priority
PackageWeight	Package weight in kilograms
Vehicle Capacity

The vehicle has a maximum capacity of:

10 kg per trip

The planner ensures that no generated trip exceeds this limit.

📏 Business Rules

The planner follows these rules:

A trip must never exceed 10 kg.

Lower priority numbers are processed first.

Deliveries going to the same area should be grouped whenever reasonably possible.

Every valid delivery appears exactly once in the generated trips.

Invalid deliveries are rejected and are not included in trip planning.

The planning process is deterministic.

Delivery IDs are generated automatically by the database.

Valid Package Weight

A delivery is valid when:

0 < PackageWeight <= 10


Examples:

Weight	Result
5 kg	✅ Valid
10 kg	✅ Valid
0 kg	❌ Invalid
-2 kg	❌ Invalid
12 kg	❌ Invalid
🧠 Trip Planning Algorithm

The planner uses a Greedy Algorithm.

Instead of trying every possible combination of deliveries, the algorithm processes deliveries one by one and selects the best currently available trip according to a fixed set of rules.

This approach was selected because it is:

Simple

Deterministic

Easy to understand

Easy to test

Easy to maintain

Efficient enough for the scope of the challenge

The algorithm does not guarantee the mathematically minimum number of trips. It is a practical heuristic that balances priority, area grouping, and available capacity.

🔢 Delivery Processing Order

Before creating trips, deliveries are sorted using:

Priority — lower number first

Area — deterministic tie-breaker

ID — final deterministic tie-breaker

Example:

Priority 1
    ↓
Priority 2
    ↓
Priority 3


This ensures that higher-priority deliveries are processed first.

🚚 Trip Selection Strategy

For each delivery, the planner checks existing trips using the following rules.

1. Same Priority + Same Area

First, the planner looks for a trip that:

Has enough remaining capacity

Contains the same priority

Contains deliveries from the same area

This provides the strongest grouping.

2. Same Priority

If no suitable trip exists, the planner looks for a trip that:

Has enough capacity

Already contains a delivery with the same priority

3. Same Area

If no priority-based trip is available, the planner looks for a trip that:

Has enough capacity

Already contains a delivery from the same area

4. Any Available Trip

If none of the previous rules match, the delivery can be placed in any existing trip with enough remaining capacity.

This helps avoid creating unnecessary trips when capacity is available.

5. Create a New Trip

If no existing trip can accommodate the delivery, a new trip is created.

⚖️ Choosing Between Multiple Suitable Trips

If multiple trips satisfy the same rule, the planner selects the trip with the highest current total weight.

Example:

Trip 1 → 4 kg
Trip 2 → 7 kg

New delivery → 2 kg


Both trips have enough capacity.

The planner chooses:

Trip 2 → 7 + 2 = 9 kg


instead of:

Trip 1 → 4 + 2 = 6 kg


This helps utilize existing capacity and reduces fragmented unused space.

🛡️ Validation and Error Handling

The API validates delivery data before storing it.

A valid delivery must satisfy:

0 < PackageWeight <= 10


Invalid values are rejected with a 400 Bad Request.

The application also uses centralized exception handling middleware instead of repeating try/catch blocks inside every controller.

HTTP Status Codes
Status Code	Meaning
200	Successful request
201	Resource created
400	Invalid request or package weight
404	Delivery not found
500	Unexpected server error

This provides consistent error handling while keeping controllers clean.

Id

PackageWeight


The Id is generated automatically by the database.

Package weight validation is enforced both:

At the API level

At the database level using a CHECK constraint

This provides an additional layer of data protection.

📈 Complexity and Scalability

For:

N = number of deliveries

T = number of generated trips

The current approach may inspect existing trips for each delivery.

Therefore, the planning process can approach:

O(N × T)


Since the number of trips can grow with the number of deliveries, the approach may become expensive for very large datasets.

Possible optimizations include:

Processing deliveries in batches

Using dictionaries for faster area and priority lookups

Reducing repeated trip scans

Avoiding unnecessary database calls

Separating data loading from trip calculation

Profiling the actual bottlenecks before optimizing

The current implementation intentionally prioritizes clarity and maintainability because these are important requirements of the challenge.

🎯 Why a Greedy Algorithm?

A greedy approach was selected because the challenge does not require a mathematically optimal packing solution.

For each delivery, the planner makes the best available local decision based on:

Priority
   ↓
Area
   ↓
Available Capacity
   ↓
Current Trip Weight


This makes the algorithm:

Predictable

Deterministic

Easy to test

Easy to explain

Simple to maintain

However:

The algorithm does not guarantee the minimum possible number of trips.

A more advanced bin-packing algorithm could sometimes produce fewer trips, but it would also introduce additional complexity.

10 kg capacity	Business requirement

Same priority + area first	Strongest grouping

Database-generated IDs	Reliable identity generation
API + database validation	Additional data protection
Centralized exception middleware	Consistent error handling
Layered architecture	Separation of responsibilities
